# StatePhase — Progress-Fill Animation

Tracks the plan (and later, implementation) for animating the phase/step progress indicators on `apps/web/components/state/StatePhase.tsx` — connectors and step cards fill top-to-bottom (and around elbows) in `blue-500` as the user completes steps, chaining across phases.

Components involved: `StatePhase.tsx`, `apps/web/components/cdl/TestSteps.tsx`.

## Background / design decisions (from discussion)

- Circles and connector lines are currently built with a **CSS border trick** (`border-l` + `border-t`/`border-b` + rounded corner), not SVG — they're elbow shapes, not straight lines.
- Layout is dynamic: step count per phase comes from the backend and varies (e.g. 4, 6, 7, 9), and column count is responsive (`mobile=1`, `tablet=3`, `desktop=variable` via `chunk()` in `TestSteps.tsx`) — row boundaries shift depending on both.
- **SVG path animation (`stroke-dasharray`/`stroke-dashoffset`) was considered and rejected**: it would need runtime path-geometry recomputation on every breakpoint change, resize, and step-count change (`ResizeObserver` + `getBoundingClientRect` per segment) — too fragile for this dynamic grid.
- **Chosen approach**: keep the existing CSS border-based connectors, but drive the fill via a **per-segment, index-ordered animation** — each segment (connector piece + step card) fills independently in sequence, using index-based delay or state-driven class toggling. Order-based, not coordinate-based, so it's agnostic to actual step count and responsive reflow.
- Row-boundary connectors (`before_row`/`after_row` in `TestSteps.tsx`) currently exist **only between rows**, not between adjacent steps within the same row. Confirmed this matches the current usage (`StatePhase.tsx` passes `columns={4}`, so 4th→5th step is a real row boundary) — but flagged as a gap: if same-row step-to-step fill is ever needed with a different column count, that connector doesn't exist yet and would need to be built.
- The phase-to-phase connector (`nextConnector` prop → trailing `after_row` on the last row of `TestSteps.tsx`) and the next phase's circle entry (`previousConnector` in `StatePhase.tsx`) are **separate DOM elements in separate component instances** that only *look* like one continuous line. Their fill timing must be explicitly coordinated, not assumed continuous.
- Completing phase 1 activates phase 2's circle styling (`phaseStatus === "active"`, `StatePhase.tsx` line 48) — already data-driven via the backend `phaseStatus` field.
- Animation must be a **real-time, one-time trigger**: plays live when the last step of a phase is completed. Must **not replay on every page load** for phases completed in a prior session.
- **Decision: backend provides an explicit signal** (e.g. `justCompleted` flag or `completedAt` timestamp) distinguishing "freshly completed, animate now" from "already completed, render final state directly." Chosen over a client-side `sessionStorage` flag for reliability across reloads/devices.
- **Refined while wiring the data model**: the mock data (`stepsmockdata.json`) had no per-step completion status at all — only a `status: "next"` marker for the upcoming step. Added `completed?: boolean` to every step (so the UI knows how many are already filled on load) and put `justCompleted?: boolean` on the **step** level, not the phase level — it's the specific step the user just finished that should trigger the animation (that step + its trailing connector, then continuing into whatever comes next). A phase-level flag couldn't express "which step" triggered it.
- **Correction after inspecting the actual connector shapes**: the earlier "overlay div + `scaleY`" plan only works on straight lines. Every real connector (`TestSteps.tsx`'s `before_row`/`after_row`, `StatePhase.tsx`'s `previousConnector`/circle-trailing div) is an **elbow/bracket** (`border-l`+`border-t`/`border-b` with a rounded corner, sometimes 3-sided). A `scaleY` transform would distort those corners. **Switched to instant per-segment `border-color` transition (white → `blue-500`), staggered by a `--fill-index` CSS custom property** (`connector-fill` keyframe/utility in `globals.css`) — each segment lights up all at once, but staggering many segments in sequence still reads as a top-to-bottom "chain" progression, and it's shape-agnostic so it works on every connector regardless of its bend.
- **Completed step-card visual**: a `blue-500` ring/border around the step's thumbnail (`step-fill-ring` keyframe/utility in `globals.css`, same `--fill-index` stagger mechanism) — chosen over a checkmark badge or dimming, to stay visually consistent with the connector fill color.
- **First real-browser check surfaced 3 bugs**, fixed:
  1. `before_row`/`after_row` are two separate divs drawn to *look* like one continuous connector across a row boundary — only `after_row` had been wired to the fill logic, so `before_row` stayed hardcoded white, making the row1→row2 connector render half-blue/half-white. Fixed by extracting a shared `rowFillState()` helper and having each row's `before_row` mirror the previous row's `after_row` state (same `--fill-index`, so both halves flip in sync). The very first row's `before_row` (which connects from the phase circle, not from another row) mirrors the phase's own `phaseActive`/`phaseJustActivated` state instead — passed down from `StatePhase.tsx` as new `TestSteps` props.
  2. The same fix extended to the connector directly below the phase circle in `StatePhase.tsx` (previously left unstyled/always-white) — now blue when the phase is active, matching the circle itself.
  3. `TestSteps.tsx` showed the premium "Gem" lock icon **and** the "Next" badge stacked on the same step when a step was both `type: "premium"` and `status: "next"`. Fixed so `status === "next"` takes priority — the lock/upgrade UI only shows for premium steps that aren't the immediate next one; once a step is next (unlocked/actionable), only the "Next" badge shows.
- **Color correction**: fill color is `blue-500`, not `blue-600` (the pre-existing phase-circle gradient `from-blue-600 to-blue-500` was left as-is — that's unrelated, existing design, not part of this feature).
- **Removed the step-thumbnail ring after a second look**: the `blue-500` ring/shadow around a completed step's image (`step-fill-ring`) was rejected on review — the image box itself shouldn't get a blue shadow. Reverted `TestSteps.tsx`'s thumbnail wrapper to its original unstyled classes and deleted the now-unused `step-fill-ring` keyframe/utility from `globals.css`. Completed-step signal is now carried entirely by the connectors (mobile per-step line + row connectors), not by anything on the card itself.
- **Two more real-data bugs, found after marking phase 1 (all 7 steps, step 7 `justCompleted`) and phase 2 (all 8 steps, no `justCompleted`) complete**:
  1. `PremiumCTA.tsx` (sits between `StatePhase` instances in `app/[state]/page.tsx` for phases 2→3 and 5→6) had its own two connector divs, entirely hardcoded white — never wired into any of this. Gave it a new `afterPhase` prop and had it call the same completion hook as `StatePhase`, so both of its connectors fill/animate off the phase they sit right after.
  2. `StatePhase.tsx`'s `isActive` only ever came from the live `previousPhaseJustFinished` trigger or the backend's own `phaseStatus` field — it had no path for "the previous phase is fully done, but that happened with no live trigger (e.g. was marked complete with no `justCompleted` step, like phase 2 here)". Fixed: `isActive` now also turns true when `previousPhaseFullyCompleted`, so a phase downstream of an already-finished phase renders pre-filled (no animation) instead of staying inactive forever.
  - **Extracted `usePhaseCompletion(phaseNumber)`** (`apps/web/lib/usePhaseCompletion.ts`) — the "is this phase just-finished / fully-completed" fetch+derivation was about to be duplicated a third time (`StatePhase`'s own phase, `StatePhase`'s previous-phase check, `PremiumCTA`'s `afterPhase` check), so it's now one shared hook all three call into.
- **Mock data reset to a brand-new-user baseline**: removed every `completed`/`justCompleted` flag from `stepsmockdata.json` (phases 1 and 2, the only ones that had them). Phase 1's step 1 carries `status: "next"` (the first actionable step for a fresh user); phase 1 keeps `phaseStatus: "active"` since the first phase is always open. All the completed/just-finished mock scenarios exercised above are reproducible again later by re-adding those flags the same way.

### 4. Trigger logic
- [x] Every animated class (`connector-fill`, `step-fill-ring`, `circle-fill-in`) is driven directly off `step.justCompleted` / `previousPhaseJustFinished` — when false, already-`completed` steps/connectors/the circle render their final blue state with no animation class at all, so there's nothing to replay

On a real backend this needs the frontend to ack (e.g. a `POST`) once the animation finishes so the flag flips false server-side and a later reload renders the static state instead of animating again. Follow-up for whenever this page gets a real API.
